# JustSearch 0.2.0 Sandbox convergence — round 1+2, and harness/process retrospective

## How to read this document

This was authored entirely inside a single ephemeral Windows Sandbox instance by an AI
agent (Claude Code), with no human in the loop reviewing the findings and **no computer-use
/ screenshot tool available in that session** (see §2.1 — this is the single biggest caveat
on everything below). It was written to be self-contained: it does not assume the reader has
access to the chat transcript that produced it. Where it says "this session" it means this one
sandbox instance's validation of candidate `0.2.0`; where it says "the repo" it means the
real `justsearch` source tree, which this sandbox never had a checkout of.

**This file was promoted into `docs/tempdocs/` on 2026-07-14 from the sandbox evidence dump**
(`tmp/sandbox/share/evidence/`), renumbered `729` → `734` (`729`, and then `730`-`733` in turn,

## Part A — Round convergence record (findings + routing)

**Candidate:** `JustSearch_0.2.0_x64-setup.exe`. **Mode:** `fresh-install` per that round's
`validation-mode.md` (no host models mapped, `JUSTSEARCH_MODELS_DIR` unset). Two rounds were
run back to back in the same sandbox instance (round 2 was a user-requested redo after a UAC
prompt was reported mid-review — see §A.4).

### A.1 [HIGH, confirmed in both rounds, three distinct symptomatic states] Dense/HYBRID retrieval never activates

**Claim it breaks:** `justsearch_search`'s MCP tool description and the README both describe
`mode: hybrid` as the default search mode, combining BM25 + dense (HNSW) + SPLADE retrieval
with cross-encoder reranking. In this candidate, dense retrieval never actually runs, in
either round, under any condition tested.

**Evidence chain:**
1. **Round 1, enrichment complete, no restart yet.** After `POST /api/ai/install/start` fully
   completed and 636 ingested docs reached `embeddingCoveragePercent: 100.0`,
   `spladeCoveragePercent: 100.0`, `chunkEmbeddingReady: true`, `pendingJobsCount: 0`,
   `GET /api/knowledge/status` still reported `embeddingCompatState: "REBUILDING"`. A
   `mode: "hybrid"` search's `searchTrace.stages` showed
   `{"id":"dense-retrieval","status":"skipped","reason":"REBUILD_IN_PROGRESS"}`.
2. **Root cause (log evidence).** `headless-backend.log` contains, at the point this got
   stuck:
   ```
   WorkerSnapshotTap: unmapped embeddingCompatState=REBUILDING; preserving prior assertion (unknown ≠ healthy)
   ```
   (`WARN`, logger `i.j.a.s.observability.health.WorkerSnapshotTap`, service `head`). The Head
   process's snapshot tap does not have a mapping for the `REBUILDING` value the Worker
   reports, and its fallback behavior is to freeze the field at its last value rather than
   propagate the new (also-unrecognized-but-real) state — so it never updates again even once
   the underlying rebuild genuinely finishes.
3. **Round 1, after a genuine cold restart** (all of: Tauri shell `JustSearch.exe`, Head
   `javaw.exe`, Worker `java.exe`, `llama-server.exe` killed and relaunched — closing just the
   shell window reconnects to the *same* still-running backend and proves nothing, see §A.4/§2.3):
   `embeddingCompatState` changed to `"BLOCKED_LEGACY"`, `embeddingCompatReason` to
   `"LEGACY_INDEX_NO_FINGERPRINT"`. `embeddingFingerprintCurrent` was populated with a real
   SHA-256-shaped value; `embeddingFingerprintStored` was an **empty string**. The restarted
   process could not find a previously-persisted fingerprint to compare against, so it treated
   the (fully enriched, 100%-coverage) index as an untracked legacy index and permanently
   blocked dense retrieval.
4. **Round 2, stronger/cleaner repro.** The round-2 reinstall reused round 1's user data
   (uninstalling only removes `%LOCALAPPDATA%\JustSearch\`; `%APPDATA%\io.justsearch.shell\`
   — models, index, enrichment state — survives by design, per ADR-0024). On this fresh
   process's **very first boot** against that already-100%-enriched pre-existing index, with
   no restart-after-ingest sequence involved at all, `GET /api/knowledge/status` immediately
   showed `embeddingCompatState: ""` and `embeddingFingerprintCurrent: ""` — a **third**
   distinct broken value — and the first `mode:"hybrid"` search immediately skipped
   dense-retrieval with `LEGACY_INDEX_NO_FINGERPRINT`.

**Conclusion:** three different surface symptoms (`REBUILDING` stuck / `BLOCKED_LEGACY` /
empty-string), observed across two independent rounds and restart conditions, all point to one
root cause: **the embedding-compatibility fingerprint is computed at runtime but never durably
persisted anywhere a fresh process reads it back from.** This is not a timing race that
resolves itself — it reproduced instantly and consistently every time a process booted against
a pre-existing enriched index.

**What still works correctly despite this:** the reranker/cross-encoder stage does fire and
does materially reorder results once triggered (confirmed via differing, including negative,
`cross-encoder` scores in the `trace` array of search results) — so "reranker never loads" is
NOT part of this bug, only the dense-retrieval leg of hybrid search. The API is also honest
about the degradation: `searchTrace.degradation.hybridFallback: true` and the exact
`hybridFallbackReason` are correctly reported both times — this is a functional regression,
not a UI/API truthfulness violation (whether the *rendered UI* surfaces this fallback to a user
could not be checked this round — see §2.1).

**Exact repro commands** (assumes backend on `127.0.0.1:8080`, some corpus already ingested and
100%-enriched):
```powershell
# Check compat state
Invoke-WebRequest http://127.0.0.1:8080/api/knowledge/status -UseBasicParsing | Select-Object -Expand Content

# Force a HYBRID query and inspect searchTrace.stages for "dense-retrieval"
$body = @{ query = "<any query that matches ingested content>"; limit = 5; mode = "hybrid" } | ConvertTo-Json
Invoke-WebRequest http://127.0.0.1:8080/api/knowledge/search -Method POST -Body $body `
  -ContentType "application/json" -UseBasicParsing | Select-Object -Expand Content
```
A genuine restart (not just closing the shell) requires killing the Head/Worker/inference
processes, not just the Tauri window — see the process-kill snippet in §2.3.

**Suggested routing:** host-tier regression test, not a `sandbox-must-watch` entry — this
condition is deterministically reproducible outside Windows Sandbox specifics (it needs no
clean-Windows-only trigger), so it belongs in CI. Two angles worth a test each:
- A live-stack test asserting `embeddingCompatState` reaches a **known-good terminal value**
  (not just that `chunkEmbeddingReady` flips true) once coverage hits 100% — covering the
  `WorkerSnapshotTap` enum-mapping gap for whatever the Worker's real "rebuild finished, safe to
  use" signal is called.
- A restart-persistence test: ingest + enrich, kill and restart the whole process tree, assert
  `embeddingFingerprintStored` round-trips and dense retrieval still activates.

**Fix record (2026-07-14, post-promotion):** implemented on this branch as `d759ad6` (certify
rebuild completion from the embedding-scoped `pending==0` fact — two consecutive reads — instead
of global queue idleness; log the previously-silent finalize waits; auto-recover BLOCKED_LEGACY
indexes by re-marking unstamped COMPLETED/FAILED docs PENDING for re-embed; map
REBUILDING/UNAVAILABLE explicitly in WorkerSnapshotTap) and `1378e92` (gate the recovery on
write-side availability). Regression homes: `InPlaceEmbeddingRebuildRecoveryTest` (end-to-end,
real Lucene/queue/counts, restart durability), stuck-PROCESSING certification test,
completed>0 recovery test, snapshot-tap mapping tests. Root-cause note: the in-sandbox
hypothesis ("fingerprint never persisted anywhere") was refuted in the narrow sense —
persistence existed and worked on the blue/green path (tempdoc 598); the defect was the
in-place backfill path's certification being coupled to global queue idleness (a PROCESSING
job, invisible in `pendingJobsCount`, blocks it forever) plus the all-pending-only recovery
precondition. Dev-stack live verification pending.

### A.2 [MEDIUM, confirmed] `collect-evidence.ps1` cannot launch the MCP Inspector CLI

`Start-Process -FilePath "npx" -ArgumentList $inspectorArgs ...` (around line 258 of the
script staged this round) fails every time with:
```
This command cannot be run due to the error: %1 is not a valid Win32 application.
```
On a standard Node-for-Windows install, `npx` resolves to a script shim, not a native binary:
```
npx.ps1   ExternalScript  C:\Program Files\nodejs\npx.ps1
npx.cmd   Application     C:\Program Files\nodejs\npx.cmd
npx       Application     C:\Program Files\nodejs\npx        <- extensionless POSIX shell shim
```
`Start-Process -FilePath` calls Win32 `CreateProcess` directly with no shell involved, and
picks one of these non-executable shim files, hence the error. A manual
`npx --yes @modelcontextprotocol/inspector --cli ...` typed directly into a PowerShell prompt
works fine, because PowerShell's own command resolution (not `Start-Process`) knows how to
dispatch `.ps1`/`.cmd` shims correctly. This was confirmed reproducible on **two separate
Node installs** in this session (the round-1 fresh install and after the round-2 collect-evidence
re-run).

**Impact:** every Sandbox round using this harness on a standard Node-for-Windows install will
show `MCP-ran: False` in the collect-evidence summary even when `/mcp` genuinely works — this
silently undermines the "mechanize capture" goal for exactly the one product surface CLAUDE.md
calls out as "the point of this release line."

**Suggested fix:** invoke via `cmd.exe /c npx <args>` (goes through a real shell that knows
`PATHEXT`/how to run `.cmd` files) or resolve `(Get-Command npx.cmd).Source` explicitly and
`Start-Process` that path instead of the bare `"npx"` string.

### A.3 [MEDIUM, confirmed] Two staged assets were missing despite being documented as staged

- **`scifact\`** — both `CLAUDE.md` and `sandbox-environment.md` (as staged in this sandbox
  instance) state a SciFact corpus is present at `Desktop\JustSearchTest\scifact\` for
  "ingest-and-quality validation." It was not present. `docs\` (631 files) was substituted as
  an ingest corpus instead. **This means no retrieval-quality/relevance benchmarking happened
  this round at all** — only mechanical plumbing (ingest completes, search returns hits,
  citations point at real files, reranker reorders results) was verified. Any future round
  reading this file should not assume `docs\`-based results say anything about ranking quality.
- **Node.js/npm/npx** — not staged in `tools\` this round, unlike Git (which had an
  exact `Git-2.55.0.2-64-bit.exe` staged and worked first try). Had to be downloaded directly
  from `nodejs.org` mid-session. This worked because the sandbox has internet access, but it
  means the `/mcp` check is implicitly exercised on a "we happened to have internet and
  nodejs.org resolved" basis, not a guaranteed offline-capable clean image, and it costs
  several minutes + a download step every round that a staged installer would avoid.

**Suggested fix:** whatever stages `tools\Git-Setup.exe` (referenced in `sandbox-launch.py` /
the sandbox staging step) should stage a Node LTS Windows installer the same way, and the
SciFact corpus staging step should be checked for why it silently produced an empty/missing
directory this round (was it a path bug, a missed copy step, or intentionally scoped out for
this particular launch and the docs weren't updated to match? — not determined from inside the
sandbox).

### A.4 [Inconclusive, not reproduced] UAC prompt during round 1's install

Partway through round 1, a human operator watching the sandbox's screen (this agent has no
screen access — see §2.1) reported having to click "Allow" on a Windows UAC (User Account
Control) elevation dialog "regarding justsearch." Asked to retry, this session:
1. Uninstalled and reinstalled JustSearch cleanly (round 2).
2. The operator confirmed the UAC dialog **did not reappear** on this clean reinstall.

Since it didn't reproduce under an otherwise-identical reinstall, this is recorded as
**inconclusive** rather than a confirmed installer defect. The most likely innocent
explanation: this session separately installed Node.js via `msiexec /i node-setup.msi /qn`
(§A.3) shortly before the operator's report, and `msiexec`-driven installs commonly trigger
UAC — the operator may have attributed that prompt to "justsearch" simply because it happened
during a JustSearch validation session, not because JustSearch's own installer requested
elevation. ADR-0024 documents JustSearch's NSIS installer as **per-user**, which normally does
not require elevation — if a future round sees this reproduce with Node.js definitely absent
from the sequence, treat it as a real installer regression against that ADR and escalate.

## Part B — Sandbox harness & process retrospective

This part is broader than a single-candidate convergence record — it's what a future agent (or
whoever maintains `scripts/sandbox/*`, `CLAUDE.md`, `.claude/skills/start/`, and
`collect-evidence.ps1`) should know about what made *this specific session* slower, riskier, or
more repetitive than it needed to be, independent of whether `0.2.0` itself has bugs.

### B.1 Environment / tooling issues

**No computer-use/screenshot tool, discovered mid-plan rather than at the start.** The Sandbox
skill and `CLAUDE.md` are built almost entirely around screenshot-gated surface coverage
("surface coverage is credited from screenshots only") and driving an actual Tauri GUI, but
this particular Claude Code session had no computer-use or screenshot tool wired up at all. This
was discovered only after a 12-item task plan had already been created assuming full UI
capability, and after already asking the user an `AskUserQuestion` about running the installer
"interactively" vs. silently — a question whose premise (that interactive GUI stepping was even
possible) turned out to be false, making that question a wasted round-trip once the real
constraint surfaced.
- **Why it matters:** any Claude Code configuration that lacks a computer-use tool but is
  pointed at this skill will silently produce an API-only validation round unless the agent
  proactively checks and flags it — which depends on agent judgement, not anything the skill
  enforces.
- **What should change:** add an explicit **Step 0** to `.claude/skills/start/SKILL.md` (before
  reading `coverage-brief.md` even): probe for a computer-use/screenshot capability (e.g. via
  `ToolSearch` for `screenshot`/`computer`/`browser` terms), and if none is found, immediately
  record that as a standing round-level gap in the mission's terms (not a decision to
  improvise) *before* any task planning or user questions that presuppose GUI access. This
  removes the need for a future agent to rediscover/re-decide this ad hoc, and stops it from
  asking questions whose premises don't hold.

**Node.js not staged, unlike Git.** `tools\` had `Git-Setup.exe` and a Chrome MSI staged, but no
Node installer, despite `CLAUDE.md` requiring `npx` for the one product surface it calls out as
most important (`/mcp`). Downloading `node-v22.14.0-x64.msi` from `nodejs.org` cost several
minutes and one transient DNS resolution failure (self-resolved on retry, likely just the
sandbox's network stack still warming up — not itself concerning, but it's an extra point of
possible failure that a staged installer would remove entirely).
- **What should change:** stage a Node.js LTS Windows installer in `tools\` the same way Git is
  staged, in whatever script populates that directory for the sandbox launch.

**The staged `scifact\` corpus was silently absent.** Both `CLAUDE.md` and
`sandbox-environment.md` (in this instance) documented it as present; it wasn't. This forced an
ad hoc substitution and means quality/relevance-of-ranking was entirely untested this round,
which the surrounding documentation doesn't surface as a risk on its own (an agent has to
notice the missing directory and reason about the consequence itself).
- **What should change:** either fix whatever staging step is supposed to place `scifact\` in
  the mapped folder, or (defensively) have `collect-evidence.ps1` / the `start` skill check for

### B.2 Repo / documentation issues

**Endpoint body shapes aren't in `CLAUDE.md`'s API table.** The table lists `POST
/api/chat/ask` with only a one-line "purpose," no field names. A first attempt used
`{"query": "..."}` (matching the sibling `/api/knowledge/search` shape) and got
`{"error":"No question provided","errorCode":"NO_QUESTION"}`; the correct field
(`{"question": "..."}`) was only found by grepping `docs/reference/api-contract-map.md`.
- **Why it matters:** every endpoint whose body shape isn't documented in the table an agent
  is told to use as its primary reference costs a guaranteed failed call + a docs detour. This
  is a small, mechanical, easily-fixed gap.
- **What should change:** either copy the exact body-field names from
  `docs/reference/api-contract-map.md` into `CLAUDE.md`'s endpoint table, or replace the table
  with a direct pointer to that file (it already has a complete `Body:` column per endpoint).

**Multi-process restart semantics aren't front-loaded where the restart instruction lives.**
CLAUDE.md's "Restart cycles" phase just says to restart; the fact that the Tauri shell
(`JustSearch.exe`), Head (`javaw.exe`), Worker (`java.exe`), and inference (`llama-server.exe`)
are four independent processes — and that closing/killing just the shell reconnects to the
*same* still-running backend, proving nothing about restart behavior — lives only in
`docs/explanation/01-system-overview.md` / `02-process-coordination.md`, which nothing in the
restart-cycle instructions points to. This session discovered the gap empirically: the first
restart attempt killed only the shell PID, and the runtime manifest's `instanceId`/`pid`
staying unchanged was the only signal that nothing had actually restarted.
- **What should change:** add a one-line pointer + the actual process-name list next to the
  "Restart cycles" step in `CLAUDE.md`, e.g.: *"A restart means killing all of: the shell
  (`JustSearch.exe`), Head (`javaw.exe` under `resources\headless\`), Worker (a second
  `java.exe`), and `llama-server.exe` if active — closing only the shell window reconnects to
  the same backend and will not exercise anything. See `docs/explanation/02-process-coordination.md`
  for why (Suicide Pact / Breath Holding)."* This turns an empirical discovery into a one-line
  read.

**`docs/how-to/cut-a-release.md`'s release index has a `v0.2.x` row pointing nowhere.** It reads
`| v0.2.x | pending | — | ... | — |` with no convergence-tempdoc link, because no convergence
tempdoc existed before this session. This document (once landed in the real repo) is that
tempdoc — the release index row should be updated to link here, but that edit could not safely
happen from inside this sandbox (see §2.4 / A.4's numbering caveat) since the sandbox's `docs\`
is a disconnected snapshot with no path back to committing into the real tree.

### B.3 Prompt / process / planning issues

**Planning got ahead of a capability check.** As covered in B.1, a full 12-task plan was built,
and a user-facing question was asked about GUI interactivity, before confirming a GUI tool
existed at all. The fix here is really the same B.1 fix (probe first), listed separately
because it's as much an agent-habit issue as a skill-documentation issue: **check hard
capability constraints before committing to a plan or asking the user a question whose premise
depends on them.**

**A user follow-up prompt this session was genuinely ambiguous and cost two clarifying
round-trips.** The operator's message was: *"i had to click allow for some permissions
regarding justsearch. retry"* — sent after the round had already fully completed, findings
written up, and JustSearch uninstalled. This didn't specify (a) which dialog (UAC / SmartScreen
/ Firewall — these have very different implications, see A.4), or (b) what scope "retry" meant
given the round was already torn down (relaunch the app? reinstall? redo everything?). Two
`AskUserQuestion` round-trips were needed to disambiguate before any useful work could resume;
guessing wrong on either axis risked either wasted rework (over-scoping to a full redo when a
narrower check would do) or an incomplete/misleading response (under-scoping and missing the
point of the report). **Exact wording that would have prevented both round-trips:** *"During
round 1's install I had to approve a UAC prompt for JustSearch — please reinstall and redo the
full validation round so we can capture that as evidence."* Naming the dialog type and the
desired scope up front turns two clarifying questions into zero.

### B.4 Verification gaps

**No search-quality/relevance verification happened at all this round**, as a direct
consequence of the missing `scifact\` corpus (A.3) — the substituted `docs\` corpus let every
*mechanical* check pass (ingest completes, search returns hits, citations resolve to real
files, reranker measurably reorders results) but nothing in this round assessed whether search
*rankings* are actually good. Anyone using this document to argue "0.2.0's search quality is
fine" would be over-reading it.

**UI-level truthfulness of the Finding A.1 degradation was never observed**, only inferred.
The API's `searchTrace.degradation` block is demonstrably honest at the API layer (it names
the exact fallback and reason every time), but whether the *rendered chat/search UI* tells a
real user "this search may be less accurate than expected" or silently presents a normal-looking
result list is exactly the kind of UI/API-disagreement `CLAUDE.md`'s mission cares about most —
and it's precisely the piece this session's missing screen access could not check (§2.1/A.5).

**Only two independent rounds, not a designed A/B.** The HIGH finding's cross-round
confirmation (A.1, three distinct symptomatic states) happened to strengthen it a lot, but this
was a side effect of an unplanned user-requested redo, not a deliberate test design. Worth
generalizing: for any `HIGH`-severity finding, a *deliberate* second reproduction under
slightly different conditions (fresh install vs. warm reinstall, as happened here by accident)
is much stronger evidence than one round's observation, and is cheap once the harness/commands
are already known — this matches the project's own rule ("verify a fix by deliberately
triggering its condition") applied to *findings*, not just *fixes*.

### B.5 Token / context efficiency (self-critique)

- **Full raw JSON dumps were read into context multiple times when only a few fields mattered**
  — e.g. a HYBRID search response containing five full result objects with multi-KB
  `content_preview` fields was read in full just to check `searchTrace.stages` and per-result
  `cross-encoder` scores. A targeted `Select-Object`/`ConvertFrom-Json` field extraction (as was
  in fact done for most *other* checks this session) would have gotten the same verification
  value for a fraction of the tokens. This session did visibly *improve* over its own course
  (e.g., the first MCP tools/list capture was read in full; the second, post-install capture was
  correctly grepped down to just `"name"` lines) — the fix is to start every log/JSON
  investigation with the targeted extraction as the default, not arrive at it after already
  paying for one full read.
- **A raw 40-line `worker.log -Tail 40` was read before pivoting to a targeted
  `Select-String -Pattern 'embed|Combined backfill'`** — the untargeted tail was mostly
  repeated, irrelevant DEBUG noise (`"Loaded analyzers catalog..."` logged multiple times per
  request). Grepping for the specific signal first would have skipped that cost entirely.
- **A large `Get-ChildItem -Recurse` jar listing was dumped, truncated to a 49.9 KB persisted
  file, and then read back at an arbitrary offset**, when the actual question ("are there
  version-mismatched duplicate JustSearch-authored jars") could have been answered directly by
  the grouping/filtering one-liner used immediately afterward, with no intermediate raw dump
  ever needed.
- **General rule worth stating plainly for next time:** when the goal is "does field X have
  value Y" or "is there a duplicate/anomaly in a large listing," write the
  filter/grep/group-by *first* and only fall back to a raw dump if the filtered view comes back
  empty or looks wrong. Don't dump-then-inspect as the default.

### B.6 Recurring mechanical friction (real, but agent-habit-fixable, not tool bugs)

- **Using the `Bash` tool to shell out to `powershell.exe -Command "..."` with `$env:`-style
  syntax inside the string mangles the path**, because Bash's own shell expands `$env` (empty
  in POSIX shells) before PowerShell ever sees the string. This happened at least three times
  this session (a `Copy-Item` call, two separate `collect-evidence.ps1` PATH-refresh attempts),
  each costing a wasted call plus a diagnosis step. **Fix:** never invoke `powershell.exe` via
  the `Bash` tool when the command contains `$env:`/PowerShell-specific syntax — always use the
  native `PowerShell` tool for anything with PowerShell variable syntax; reserve `Bash` for
  genuinely POSIX-shell work (file globs, `wc -l`, etc. against paths that don't need `$env:`
  expansion).
- **Shell state (`$env:Path`, etc.) does not persist between tool calls**, so after installing
  Node.js via `msiexec`, nearly every subsequent `PowerShell` call that needed `node`/`npx` had
  to re-run `$env:Path = [System.Environment]::GetEnvironmentVariable(...)` first. This is
  documented tool behavior, not a bug, but it was forgotten at least twice this session, each
  time producing a confusing "`npx` not found" failure immediately after `npx` had just worked
  fine in a different call. **Fix (agent habit):** immediately after installing anything that
  changes `PATH`, either resolve and reuse the absolute exe path for the rest of the session
  instead of relying on bare command resolution, or treat the PATH-refresh line as a mandatory
  prefix on every subsequent call that shells out to that tool.
- **Killing processes by bare `ProcessName` pattern-match (`"java|JustSearch|llama"`) is riskier
  than necessary.** It happened to be safe in this single-purpose, throwaway sandbox VM (nothing
  else was running), but the pattern generalizes badly — a shared or less-controlled environment
  could have an unrelated process matching the same generic name. **Fix:** prefer matching on
  the process's `Path` (e.g., filter to `Path -like "*\JustSearch\*"` or
  `*io.justsearch.shell*`) over bare name, even when the current environment happens to make it
  safe not to.

### What worked unusually well (preserve these)

- **Recognizing the "no GUI tool" blocker and stopping to ask, rather than either faking UI
  verification or silently grinding on workarounds.** This produced an honest, well-scoped
  round instead of a misleading one. The `AskUserQuestion` framing (three concrete options:
  build a fragile PowerShell-automation fallback, have the human drive the GUI, or go
  API-only-and-flag-the-gap) let the user make an informed tradeoff instead of the agent
  guessing.
- **Explicitly documenting every gap as a gap, not silently absorbing it.** The npx harness bug,
  the missing `scifact\` corpus, the missing GUI tool, and the inconclusive UAC prompt were all
  written up as their own named items rather than smoothed over — directly following the
  project's own "don't apply a workaround without documenting the failure it hides" rule.
- **Chasing the HYBRID-search anomaly down to an actual log line and root-cause hypothesis**
  instead of stopping at "the field says something odd." Grepping `headless-backend.log` for
  `WorkerSnapshotTap`/`embeddingCompatState` turned a vague "search seems degraded" observation
  into a specific, reproducible, root-caused finding with a concrete suggested fix.
  This matches the project's own "verify positively" and "stderr/logs are data, not noise"
  rules, applied well.
- **Background polling via `run_in_background` + blocking `TaskOutput`** for the ~20-minute
  Install AI download and the enrichment-completion wait, instead of any foreground
  busy-waiting. This respects the platform's guard against long foreground `sleep`s and is the
  correct pattern for any long-running Sandbox operation whose duration is unknown up front —
  worth reusing as-is in future rounds (just pick a longer per-call deadline than was used here,
  see B.5-adjacent note: two relaunches were needed for the ~20 min download and three for
  enrichment completion because each poll loop's internal deadline was only ~9 min; a ~25–30 min
  deadline per call would have covered the whole wait in one shot with no loss of correctness).

broken.** On the OLD 0.2.0 build under test, an expired `PendingAuthorization` still produced a

  unknown/expired/already-consumed `pendingId` — the `pendingStore.consume(id)` empty branch
  (`modules/ui/src/main/java/io/justsearch/ui/api/AuthorizationController.java:151-159`).
- The MCP peek bridge skips 404s rather than presenting a broken prompt
  (`modules/ui-web/src/shell-v0/operations/pendingAuthorizationBridge.ts:122-134`).

coverage on either side before this round, verified only by the live GUI smoke pass above. Backend:
`AuthorizationControllerTest#approve_unknownPendingId_returns410WithErrorBody_noCapsuleMintedNoDispatch`

## Part C — Round economics: what may a round spend itself on? (design, 2026-07-15) — **TOMBSTONED, see Part F**

> **Superseded.** D.1 refuted this section's premise (the causal link was never established) and Part E showed the stronger move is structural. Kept because the reasoning that killed it is the useful part; do not build from it. The design is **Part F**.

**Thesis.** Four rounds, none shipped. A round costs an installer build, a sandbox launch, hours of agent time, evidence extraction and analysis. Its scarce resource is **facts only a real install on a clean machine can establish**. Every check that spends a round on something a host-side test already owns is not merely waste — it displaces a fact only the round could have produced.

**The clinching evidence is F-3.** Its regression home is *already* a backend unit test asserting on captured `Level.WARN` events (`RuntimeActivationServiceTest:240-307`). Meanwhile the round left four required shapes (`agent-run`, `extract`, `free-chat`, `workflow-run`) unexercised — coverage only a round can get.

**Design.** Every round item declares its **tier** and, when it claims round-only, *why nothing host-side can prove it*. The register already has this vocabulary: `install-trust-prompts` carries `observability: blocked-by-posture` with the posture reasoning inline, validated by `ALLOWED_MUST_WATCH_OBSERVABILITY` in `gen_coverage_brief.py`. **Falsifier.** Round-over-round, the share of findings that were host-detectable should fall and required-shape coverage should rise. If round count doesn't drop within two rounds, this design is wrong — delete it.

**Explicitly not this design's job:** deciding *which* items are round-only. That is the output of applying it, not an input.

## Part D — Theorization before Part C settles (2026-07-15)

Ideas and framings, not a design. Recorded so the design can be argued with rather than inherited. **Part C as written above is challenged here by its own author**; read D.1 before building anything from C.

### D.1 Part C's thesis does not survive its own evidence

Part C claims a round's redundant checks *displace* facts only a round can produce, citing four unexercised shapes. **The causal link is not established.** The round's own postmortem says its task list was built from the operator's prose, not from the generated `coverage-brief.md` — so the four shapes were missed by **derivation failure**, not by displacement. `derive_round_plan.py` already addresses that directly.

Two claims were being conflated:

- **(a) Rounds contain redundant and unfalsifiable checks.** True, evidenced (F-3).
- **(b) That redundancy is why rounds don't ship.** Unproven, and probably false.

This is `interrogate-results` failing in the place it is hardest to notice: the evidence matched the hypothesis, so nobody dug. Recorded as an instance, not just a correction.

**What actually stopped rounds 1-4 shipping: the product had bugs.** Rounds 1-2 died on dense retrieval, round 3 on 3 HIGH + 6 MEDIUM, round 4 on the capability gate. The rounds *worked*. Four rounds to converge a first desktop release may not be a pathology at all — that possibility deserves stating, because "the loop is too slow" is an assumption, not a measurement.

### D.2 The stronger reframe: the round has been a census of missing tests

Of the eleven distinct defects rounds 1-4 surfaced, **eight were fixable with a unit test — and every one of those got a unit test as its fix**: palette omission (`actions.test.ts`), health row (`SystemSelfView.test.ts`), false WARN (`RuntimeActivationServiceTest`), Activity SSE binding (`resourceListItem.test.ts`), theme resolution (`themeState.test.ts`), the indexing trap, encryption copy (`SecuritySurface.test.ts` — **net-new**), stale DATA PROTECTION row. Several test *files* did not exist before the fix.

So those surfaces shipped with no test at all, and the round was **the first thing that ever exercised them**. The round was not finding bugs so much as discovering the absence of a tier. Only three were genuinely round-tier: A.1 (fresh install + real model), INS-005/CUDA (install integration), and arguably the capability gate.

That reframes the round's output: not a defect list, but a **coverage map of what nobody tested**.

### D.3 …and the obvious conclusion from D.2 is wrong

The naive rule — *"an item with a host-side regression home should be dropped from the round"* — fails on this branch's own headline example. **A1 had unit tests and still needed the round.** Five of them, four proven red by revert, and the button was dead anyway: the tests could not see the capability gate two layers down.

So test-existence does not set the tier. What distinguishes A1 is that its property is **not local** — it spans UI branch → operation catalog → capability resolution → runtime state. No single layer's tests can see it, so every layer can be green while the feature is dead.

**Candidate principle: a property's verification tier is set by its locality, not by its importance.** The round's proper subject is properties that are cross-layer or environment-dependent — the ones no cheaper tier can *see*.

### D.4 The deeper move: reduce non-locality instead of tiering the checks

If D.3 holds, Part C is a symptom-level fix. Tiering checks accepts non-locality as given and rations the expensive tier around it. The root move is to make the property local, after which no round check is needed at all.

A1 again: rather than have a round click "Resume" every cycle, make "an operation must not require the capability its own success establishes" a **build-time** check (tempdoc 737 §4's probe, promoted to a gate). Then the property is local, mechanically enforced, and the round never spends on it.

- **Moving the property beats moving the check.** This is `fix-root-causes-not-symptoms` applied to the harness itself.
- **Corollary linking 734 and 737:** round burden is roughly inversely proportional to how local the system's properties are. If 737 succeeds, the round shrinks as a side effect. Neither doc should design as though the other doesn't exist.

Honest counterweight: `static-green ≠ live-working` is real and round 4 proved it — unit-green fixes were live-dead. Locality reduces what the round must check; it never empties it. Over-moving is a real failure mode with its own name already in the repo.

### D.5 Why the round needs so much anti-lying machinery — a unifying observation

Almost everything shipped today (size floor, cross-token duplicate detection, the retrospective gate, staging ratchets, `click.ps1` failing closed) exists to stop a round asserting something untrue. That is not incidental. **The round is the only verification tier whose result depends on an agent's honesty and attention.** A unit test, a gate, an ArchUnit rule and a lint either pass or fail mechanically; a round can be *wrong without failing*.

This reframes the motive for moving work off the round: not cost, but **trustworthiness**. A check that can be made mechanical should be, because the round is the one tier that can be confidently wrong — as it was on Finding 1, and as this branch's own agent was on A1.

### D.6 Independence, not mechanism, is what catches what mechanism can't

The filename-lies-about-content gap has no mechanical answer (the bytes are unique and internally consistent). What caught it was an **independent pixel reader** — and it caught it *not because it was more capable*, but because it had no stake in the round's verdict and had not written the evidence. Same for this branch's own errors: subagents contradicted their briefer's framing five times today, correctly, every time on primary sources.

**Candidate principle: for tiers that can lie, independence substitutes for mechanism.** Note the repo already learned this twice — `independent-reviewer-required` and `ux-audit-closure` were both gate-enforced and both retired to honor-system (tempdoc 563). Round 4 is a third instance arguing the same thing. Worth asking whether the retirement, not the rule, was the mistake; that question belongs to whoever revisits the gate kernel, not here.

### D.7 The collision tension — duplication was the cost *and* the detector

Part C proposes a `git merge-tree` collision preflight because #185 and this branch independently diagnosed the same bug. But note what actually happened: **the duplication is what caught the error.** Two independent diagnoses disagreed, and the disagreement exposed a fix that fabricated provenance. Had this branch deferred on seeing "someone is already on this", `main` ships broken.

So the preflight must **inform, never allocate**. A mechanism that prevents duplicate work would have suppressed the only signal that found the bug. This is D.6 restated from the other side: independent duplicate effort is expensive *and* is an error-detection mechanism, and the tradeoff should be made deliberately rather than optimised away because duplication looks like waste.

### D.8 Risks and hidden assumptions in anything built from Part C

- **Goodhart.** If rounds are ever *scored* on "share of findings that were round-tier", the round is incentivised to under-report host-tier findings. Any such metric must be computed from fix commits, by the harness, and never be visible to the round.
- **Survivorship.** "8 of 11 were host-detectable" is only knowable because someone wrote the test afterward. Defects never found, or found and not fixed, are absent from the denominator. The ratio is suggestive, not a measurement.
- **Register-as-fork.** A mapping of round item → owning test is a second authority that will drift from the tests themselves (the exact failure `execution-surfaces` exists to prevent). If an item names its test, a gate must assert that test *exists and is green*, or the mapping becomes decoration.
- **The unfalsifiable-check class is probably not just F-3.** F-3 was found by accident while verifying something else. Nothing has swept the item set for other checks that structurally cannot fail. That sweep is cheap and is probably worth more than any new mechanism.

### D.9 Open questions worth answering before Part C is designed

1. Is round *count* actually the problem, or is it round *duration* and *analysis* cost? Nobody has measured where a round's hours go.
2. Is a round's finding distribution clustered by subsystem? If most cluster in the AI-runtime lifecycle, the leverage is 737, not the harness.
3. How many other round items are structurally unfalsifiable (F-3's class)? Sweep before designing.
4. Would the honest metric be "findings whose regression home ended up host-tier", computed retroactively from the fix commits of rounds 1-4? That is answerable **today**, with no new mechanism, and it would settle D.2 with data instead of recollection.

## Part E — Research pass: what the prior art and a real count say about Part D (2026-07-15)

Three independent passes: a census of our own fix commits, and two external literature reviews. **Part D survives in substance and is wrong in most of its specifics.** Recorded with citations so a reader can check rather than trust.

### E.1 The census: D.2's numbers were wrong, and the claim is stronger than stated

An independent agent recounted from `git show` / `git log --diff-filter=A` against every fix commit, not from this document's prose.

- **14 distinct defects, not 11.** D.2's arithmetic is **not re-derivable from this document's own tables**: the round-3 findings table lists 10 fixed findings, but D.2 names 8 and silently drops **NEW HIGH** (encryption breaking the thread projection) and **O-2** (query text in the exported log) from both its buckets. They vanish.
- **12 of 14 (86%)** were fixed with a unit test in their regression home — not 8/11 (73%). The two exceptions are the capability gate and Finding 2, both **still open with zero coverage because they are unfixed**.
- **Six surfaces had zero prior test coverage of any kind**, not one as D.2 says: F-6, F-7, O-2, F-4's `ActivitySurface.render.test.ts`, F-8, and NEW HIGH's FE half all added a wholly new test file.

So D.2's qualitative claim — *the round has been a census of missing tests* — holds under independent recount and is **better supported than the version that asserted it**. Its figures were recollection, and they were wrong in both directions.

Note the shape of this error: D.8 warns that a hand-maintained mapping of item → owning test is "a second authority that will drift." **D.2 was that fork, and it drifted, inside the same document, within hours.** Recorded as an instance rather than quietly corrected.

### E.2 The A1 counterexample holds, verified independently

`BrainSurface.indexing-escape.test.ts` (net-new, 123 lines) mocks the dispatcher:

```ts
invokeOperation: (operationId, args) => { invocations.push(...); return Promise.resolve({ structuredData: null }); }
```

It **always resolves**. All five assertions are about *what the FE dispatches*; none about *whether the dispatched operation can execute*. The four-layer chain was re-verified at the cited lines (`CoreOperationCatalog.java:803` → `HeadAssembly.java:1211` → `capabilities.inference().available()`, false precisely in the only state from which the button is shown).

These are not weak tests — four fail on revert, so they exercise real logic. It is a test whose **scope** cannot reach a defect three layers downstream. The locality account stands.

### E.3 Survivorship is structural, and it bit this document

A fix-commit census **cannot see a defect that was found and not fixed**. Two such defects exist in this very document — the capability gate and Finding 2 — and D.2 omitted both. **A fix-commit census undercounts round value by construction.** Any metric built on this method inherits that, and D.8's survivorship warning is confirmed rather than theoretical.

Also: **"host-testable" is not binary.** A.1 and INS-005 are *partly* round-tier — the logic bug was host-testable and is now tested; "does a real download and restart actually behave" genuinely needed the round. D.2's single-bucket framing loses this.

### E.4 We are NOT reinventing contract testing — and reaching for it would be a mistake

- **Rainsberger, "Integrated Tests Are a Scam"** (talk 2009/2013; "Clearing Up the Integrated Tests Scam", The Code Whisperer, 2015-12-08). His thesis is an *incentive/feedback* argument, and his replacement is a **pair**: collaboration tests (client against a double) + contract tests (the real collaborator against the same expectations). Unit of analysis: **two collaborating parties with an interface**. He explicitly keeps a small number of integrated tests, and scopes the critique to programmer-facing tests.
- **Consumer-driven contracts** (Fowler, 2006-06-12; Pact docs). Explicitly a **cross-process, wire-boundary** pattern between independently-deployable parties. Documented failure mode: mock-vs-real drift.

**Our bug has no two-party interface.** It is a cycle across a declared-metadata layer, a resolver, and runtime state *inside one process*. There is no consumer/provider pair to write a contract between "a UI branch" and "runtime state" — which is exactly why four green layers coexisted with a dead feature. Applying CDC here would be cargo-culting the name of a solved problem onto an unsolved one.

### E.5 Our shape *does* have established names — none from the testing literature

- **Petri-net / workflow-net soundness** (van der Aalst). A transition requiring a token only its own firing produces is a **structurally dead transition**, provably unfireable by siphon/structural analysis **without executing anything**. Decidable at design time. Strongest match; 30+ years of tooling.
- **PDDL/STRIPS action-precondition reachability.** Our operation catalog is structurally a planning domain (operations = actions, capabilities = predicates, requires = precondition, establishes = effect). An action whose precondition is satisfiable only by its own effect is flagged **unreachable** at domain-authoring time.
- **DI-container circular-dependency detection** (Spring ≥2.6, Guice) — the mainstream engineering analogue, failing fast at startup on the same graph shape.
- **Design by Contract** (Meyer) supplies the vocabulary but not this cycle as a named failure mode.

So D.4's instinct — promote it to a build-time check — is **the field-recognised right move**, not a novelty and not an anti-pattern. This belongs in tempdoc **737 §4**, as a fitness-function/gate over the catalog graph, not in the round.

### E.6 The caution that lands on 737, arriving from outside

A static check over **declared** capabilities is only as good as the catalog remaining the source of truth. If the resolver's real behaviour can drift from the declaration, the check gives false confidence **exactly as an unfaithful test double does** — *Software Engineering at Google* frames this via **Hyrum's Law**: the effective contract is all observable behaviour, not the stated one.

**Therefore: prefer generating the catalog from the resolver's real behaviour over hand-maintaining it** — which is precisely what DI containers do (they inspect real constructor signatures, not a hand-maintained doc). This is our own projection-vs-fork rule, reached independently from the literature, and E.1 just demonstrated the fork failure mode on ourselves.

### E.7 "Locality" is our coinage; the published framing is Size vs Scope

No primary source uses "locality" this way. The nearest published framing is *Software Engineering at Google* ch. 14's **Size** (resources/hermeticity) vs **Scope** (code graph) split, whose stated rationale for larger tests is **fidelity, not importance** — and which names exactly our failure classes: emergent behaviour, configuration ("the number one reason for our major outages"), Hyrum's Law, unfaithful doubles. Say "our restatement of Google's Size/Scope", not "the locality principle", in anything public.

The literature also genuinely **disagrees** with itself: Rainsberger says push weight *down* into collaboration+contract pairs; Dodds' Testing Trophy and Spotify's honeycomb say push weight *up* to the integration layer because that is where real bugs cluster. Both camps agree on the diagnosis (narrow tests miss seams) and differ on the remedy. Our defect is evidence for the shared diagnosis, not for either remedy — it isn't at a two-party seam at all.

### E.8 D.6's mechanism is wrong — and the better one is more damning

D.6 attributed the pixel-reader catch to self-preference bias. The better-fitting mechanism is **generator/evaluator shared failure mode**: Huang, Chen, Mishra, Zheng, Yu, Song, Zhou, *"Large Language Models Cannot Self-Correct Reasoning Yet"*, arXiv:2310.01798, **ICLR 2024**. The same "trust the filename I gave it" assumption that mislabelled the screenshot is what validated it at coverage-check time. **Correlated error, not vanity.**

And the self-preference literature is softer than D.6 assumed:

- **Zheng et al., MT-Bench/LLM-as-a-Judge, arXiv:2306.05685 (NeurIPS 2023)** coined "self-enhancement bias" (~10pp GPT-4, ~25pp Claude-v1) — but *its own authors hedge*: the study "cannot determine whether the models exhibit a self-enhancement bias." The widely-cited number was never confirmed by the paper that produced it.
- **Panickssery, Bowman, Feng, arXiv:2404.13076 (NeurIPS 2024)** is the firm result: self-recognition is a *causal lever* on self-preference.
- **Wataoka et al., arXiv:2410.21819** reframes much of it as **perplexity/familiarity** preference — favouring in-distribution text whether or not it is self-authored. If so, hiding authorship does not remove it.
- A 2026 multi-judge study found **~0.2% residual in-group bias** after normalisation — i.e. a genuine quality gap, not bias.

**Most importantly: same-model-but-independent is NOT an established mitigation.** Multi-agent debate among same-model copies, without a decorrelating intervention, performs no better than plain self-consistency. One peer-reviewed paper (Choi/Zhu/Li, ACL 2026) supports **anonymisation** as the operative lever; an industry study reports anonymisation failing because the mechanism is perplexity-driven. That tension is real and unresolved, and **nobody has studied our task type** — factual/perceptual "does this image match its filename" — as opposed to the chat-quality comparisons this literature actually measures.

### E.9 The name is centuries old, and there is an off-the-shelf pattern

- **Audit: "self-review threat"** — one of five canonical independence threats (IESBA/IAASB), structurally identical: the auditor who prepared the statements cannot properly audit them.
- **ISTQB "independence of testing"** — a ready-made escalation ladder (author → peer → dedicated team → external), with the caution that *independence is a trade-off, not free*: authors find many defects in their own work efficiently.
- **IIA: "Self-Assessment with Independent Validation"** — the closest existing pattern to what D.6 proposed, already named.

Best framing for our docs: the round carries a **self-review threat**, instantiated as **zero independence of testing**, manifesting as **generator/evaluator shared failure mode**.

### E.10 What this does to Parts C and D

1. **Do not build Part C as written.** Its thesis is unproven (D.1) and its mechanism is the weaker of the two available (E.5). The stronger move is structural checks over the declared graph, owned by 737, plus continuing to migrate properties down a tier as rounds reveal them — which is what we already did for 12 of 14.
2. **Do not mandate the independent-review gate on this evidence.** The mechanism was misdiagnosed (E.8), the mitigation is unvalidated for same-model independence, and our task type is unstudied. `audit-driven-fixes-need-test`, applied to our own proposal.
3. **Run the experiment instead — we already have the materials.** Plant known-bad artefacts in an evidence set at a controlled rate; compare catch rates across (a) the producing agent self-grading, (b) a fresh same-model instance with no authorship, (c) a different/stronger model, (d) repeat runs of (b) for stability. Round 4 supplies a real known-bad artefact for free (`43`/`44`, a command palette credited as the logs surface). That answers it for **our** task type, which the literature does not.
4. **Open, unsettled:** whether an LLM judge is stable enough on repeated identical inputs for a single independent pass to be trusted at all — a "catch" could be noise. Any gate needs test-retest data first.

## Part F — Design: give the round a bite (2026-07-15)

Supersedes Part C. Written after the Part E research pass and two codebase investigations. General by intent; implementation belongs to a plan, not here.

### F.1 The problem, as it actually stands

Not *"which checks may a round spend itself on"* — that was Part C, and D.1 refuted its premise. The problem this document actually has:

> **The round is the only verification tier that can be wrong without failing, and we have never measured how often it is.** We shipped ~14 harness mechanisms in one day on the strength of reasoning. Each was demonstrated against a fixture we handed it. None has been measured against a round.

That is not a gap in coverage. It is a gap in **knowing whether any of this works**.

### F.2 The repo already has this principle — four times. Conform to it.

An investigation (read-only, `file:line`-cited) found that *"plant a known-bad thing, prove the check catches it"* is **already a first-class, gate-enforced concept here**:

| Layer | Mechanism | Real? |
|---|---|---|
| Hooks | `hook-integrity`'s **bite** — spawns the hook with crafted violating stdin, asserts the exit code (`gates/hook-integrity/enforcer.mjs:65-103`); a `role:blocking` hook with no `bite` spec fails the build (`truth-table.mjs:88-98`) | **Yes** for `kind:'command-signal'` |
| Gates | Every gate ships `scripts/governance/_fixtures/<gate-id>/{positive,negative}/` + an `enforcer.test.mjs` asserting fail-on-bad / pass-on-good — **169 fixture files** | Yes |
| Unit tests | `test-efficacy` / PIT mutation testing over the 12 registered seams in `governance/logic-seams.v1.json`; `strength = (KILLED+TIMED_OUT)/(KILLED+TIMED_OUT+SURVIVED)`, ratcheted upward, changeset required to accept a drop | Yes |
| Individual hooks | firing / non-firing corpora inside `*.test.mjs` | Yes |
| **The round** | — | **Nothing** |

So the design is not an invention. **The round is the one verification tier in this repo with no bite proof**, and the house pattern already says what one looks like.

Two honest findings from that investigation, both recorded rather than smoothed:

- **`bite` overclaims itself.** `kind:'unit'` bites only `existsSync(testPath)` (`enforcer.mjs:195-197`) — the test is never executed. The enforcer's docstring (`:11-12`) claims bite "proves the hook EMITS its block signal", true only of the `command-signal` half. Logged to the inbox; not this tempdoc's to fix.
- **The canary is not a positive control.** `mcp-canary*.txt` is hand-authored, created by no script, and appears only as *retroactive prose* explaining why docCount was 5190 rather than 5189 (`sandbox-CLAUDE.md:254-265`). Nothing ever asserts it was found. It is a footnote, not a control.

### F.3 736 is not prior art — do not cite it as such

Tempdoc 736 ("agent-eval capture & instrument integrity") is the nearest title and the wrong doc. Its thesis is **record self-description** — digest coverage, tombstones for structurally-ineligible records, which denominator is primary, four-state status. Its P1-P3 principles each carry a retirement condition and **none addresses catch rate**: they govern what a record declares about itself, not whether a checking mechanism detects anything. Its denominator work solves *"which known count is primary"*; our survivorship problem is *"the numerator and denominator both omit what nobody found"* — a different problem in the same vocabulary.

Four tempdocs (726, 730, 731, 736) use "integrity" for four unrelated technical concepts (checksums, worker lifecycle, retrieval labels, capture fidelity). **Coincidence of a popular word.** The one real link is `731:386` routing eval-harness code to 736's ownership — an area pointer, not a shared framework.

The mandate for this design is **E.10.3**, in this document.

### F.4 The design

**Give the round a bite: plant known-bad artefacts of registered classes, and measure which tier catches them.**

Four parts. The first three are the instrument; the fourth is the point.

1. **A register of known-bad artefact classes.** Structurally a sibling of `governance/logic-seams.v1.json` (which registers what PIT is allowed to mutate). Each class declares: how an instance is planted, what it should look like to a reader, and **which tier is claimed to catch it**. Round 4 supplies three classes for free, all *observed*, none invented:
   - `mislabeled-capture` — filename claims one surface, pixels show another (`43`/`44`: the logs surface credited by a screenshot of the command palette).
   - `blank-capture` — a structurally valid image with no UI in it (`02`, 8,554 bytes).
   - `duplicate-credit` — byte-identical images crediting different required tokens.

2. **A plant mechanism.** Seeds instances into a round's evidence path at a controlled rate. Nothing in the repo does this today.

3. **Ground-truth bookkeeping.** *(artefact, class, planted-at)* → so a miss is attributable rather than arguable. New.

4. **Cross-tier scoring — the genuinely new piece.** For each planted defect, independently record whether it was flagged by **(a)** the mechanical gate (`check_coverage.py`), **(b)** the round itself, **(c)** an independent reader with no authorship, **(d)** a different/stronger model. Every existing bite instance asks *"did tier N catch it?"*. **None asks "did tiers {gate, round, reader} catch the same defect, and where did they diverge?"** — and that divergence is the whole question: it settles both whether our mechanical harness earns its keep, and Part E's independence experiment, from one seeded set.

Numerically, borrow PIT's arithmetic: **catch rate = flagged / planted**, per class, per tier. Same math, different unit.

### F.5 Scope: what this design does *not* build yet, and why that is not deferral

The house pattern's full shape is report → baseline → direction-aware enforcer → one-directional ratchet + changeset. This design **stops before the ratchet**, for one reason: *a ratchet pins a baseline, and we have never taken a single measurement.* You cannot defend a floor you have never stood on. The ratchet is the natural home for the result and conforms when it arrives; building it now would be apparatus around an empty number.

This is not the "wait-for-more-evidence" move `structural-defects-no-repeat` forbids. That rule bars deferring a *correctness fix* pending more incidents. Here the input to the mechanism does not yet exist.

Steal one thing from `expected-state.v1.json` without adopting its schema (wrong polarity — it registers known-*red*, we need known-*bad-artefact*): its **pin-expiry discipline**, where every pin carries a mechanical probe or a human review date so nothing rots silently.

### F.6 What this orphans — deletions belong to this tempdoc — **PARTLY CORRECTED, see H.2** (the canary teardown is near-vacuous; removing the cited paragraph wholesale would destroy an unrelated, valuable calibration warning)

- **Part C** — the tier-declaration design. Never built; superseded by E.10 and F.4. **Tombstoned above**, not deleted, because the reasoning that killed it is the useful part. Its one salvageable element (`observability: blocked-by-posture`) already exists in the register and stays.
- **The ad-hoc canary.** If plants become first-class, `mcp-canary*.txt` becomes the register's first *positive-control* class, and the hand-authored files plus the retroactive docCount prose at `sandbox-CLAUDE.md:254-265` are **deleted** — not left as a second, informal way to do the same thing.
- **"Make independent pixel review a required finalize step."** Proposed earlier in this document on the strength of one lucky subagent. **Withdrawn** by E.8 (the mechanism was misdiagnosed; same-model independence is not a validated mitigation) and replaced by F.4's measurement. Do not re-propose it as a gate before the instrument reports.

### F.7 Design constraints and honest limits

- **A plant the round can recognise as a plant measures nothing.** If a seeded defect is distinguishable from a real artefact — by filename convention, by a marker, by living in a manifest the round can read — the round's catch rate is theatre. **Therefore: ground-truth bookkeeping must live host-side and must never be staged into the sandbox.** This is a hard constraint on the design, not an implementation detail.
- **The instrument is bounded by our imagination.** Seeded classes only measure defects someone thought to seed — structurally the same survivorship hole that embarrassed D.2 (E.3). Mitigation, and it is only partial: **register a class only when a round has actually produced an instance of it.** Never invent one. The register then grows from evidence, in the same spirit as `structural-defects-no-repeat` — one documented instance proves the class.
- **Judge noise may swamp the signal.** E.10.4 stands: if a reader's verdict is unstable on repeated identical input, a single "catch" is partly luck. Repeat runs of the same tier are part of the instrument, not an optional extra.
- **This measures detection, not correctness.** A tier that catches every planted defect may still miss every real one. Catch rate is a lower bound on blindness, not an upper bound on quality.

### F.8 Reach — the principle, and who violates it — **CORRECTED, see H.1** (the harness Python checks DO have real executed bite proofs; the true finding is that nothing ever runs them)

The repo instantiates one idea four times without naming it once. Name it in the repo's own vocabulary rather than coining a rival:

> **Bite: every verification mechanism must demonstrate that it catches a known-bad input — and the demonstration must execute, not merely exist.**

**Where it already applies, and who violates it today:**

| Site | Status |
|---|---|
| Hooks (`command-signal`) | Conforms — executes |
| Hooks (`unit` kind) | **Violates** — `existsSync` only; proves a file exists, not that the hook bites |
| Governance gates | Conforms — 169 positive/negative fixtures |
| Registered logic seams | Conforms — PIT kills mutants |
| Unit tests outside those 12 seams | Unmeasured — no claim either way |
| **The sandbox round** | **Violates** — this design |
| **The harness's own Python checks** (`check_coverage.py`, `check_golden_parity.py`, `derive_round_plan.py`) | **Violates** — they sit outside the governance `_fixtures` convention entirely, and they are exactly the checks that credited a palette screenshot as the logs surface for four rounds |

That last row is the most useful thing this design surfaced, and it is **cheaper than the instrument**: the harness's own gates could get bite proofs today, by the existing fixture convention, without planting anything into a live round.

**Do not build the generalised structure now.** The principle is recorded; the two violators are named. Fixing the harness checks' bite is small and in-scope. Promoting `unit`-kind hook bites to executed proofs is the hook layer's, and is logged.

**Evidence it earns its keep:** a mechanism whose measured catch rate is zero across rounds gets **deleted** rather than kept for comfort. If the size floor or duplicate detection never fires on a real round, they were reasoning, not protection, and this principle is what tells us so.

**Retirement condition:** if seeded classes never diverge across tiers — every tier catches everything, or nothing does — then the cross-tier comparison is decoration. Delete it and keep only the cheapest tier's bite proof. Equally, if the register only ever grows with classes we invented rather than observed, the instrument has become calibrated against our imagination and should be retired rather than trusted.

## Part G — Derisk: what we measured instead of assumed (2026-07-15)

### G.1 Closed: `lambdamart.not_configured` is benign by design

LambdaMART is trained *locally per install* from the user's own corpus (`LambdaMartReranker.java:25-40`, via `GplJobCoordinator`) — it cannot be pre-shipped, so DEGRADED is every fresh install's permanent state. ### G.2 Closed: there is NO minimal capability-gate unblock — and it is a class

1. **Each machine optimizes its own graph locally** (`first run or cache stale`). Two separately

### Verdict: **DO-NOT-QUALIFY** — a HIGH-severity ingest livelock (round 7's finding 2)

The second folder a user adds **silently never indexes, forever**, while every health surface
reports green. It is not a stall: the worker sits at 100% of one core doing work indefinitely,
which is exactly why nothing reported unhealthy. `IndexingLoop.runLoop()` is the only caller of
`jobQueue.pollPending(...)`; on an empty poll it enters `BackfillScheduler.runIdleCycle()`, an
**unbounded** tight loop whose only exits are shutdown, `isUserActive`, and
`shouldYieldGpuBackfill` — no iteration bound, no time budget, no no-progress detector, and no
check for pending ingest jobs. Its continue-condition is `anyWorkDone()` = `written > 0`, which is
not a progress measure: a document that is rewritten but never advances pins it true forever.

The non-terminating input is a status ping-pong on chunk documents. Chunk docs are written with no
`embedding_status` and no `ner_status`; the blank-content branch defaults an *absent* status to
`PENDING` and then stamps `COMPLETED` with no artifact ever produced; the 717/711 RMW preservation
lanes correctly detect those lies and re-arm them to `PENDING`. Two mechanisms each correctly
"repairing" the other's write, forever:

| pass | update map written | RMW side effect |
|---|---|---|
| A | `{embedding_status: COMPLETED}` | splade lane resets `splade_status` → PENDING |
| B | `{splade_status: COMPLETED}` | vector lane (null vector) resets `embedding_status` → PENDING |

Log corroboration: the identical `Combined backfill` line repeats ~64×/second from `17:22:57.654`
onward — 59,420 such lines in `worker.log.1` alone, **zero WARN and zero ERROR across the entire
window**, and the `withNrtSuspended` bracket entered once and never left until shutdown. The two
"occurrences" the round first recorded were not two bugs: they are the two moments an ingest
happened to land during one continuous livelock that began at ~17:22 and never ended.

**Regression window:** the second half of the ping-pong shipped 2026-07-12 in `d37578a8` (717),
which changed `vector`'s policy to `preserve-reread-or-reset:embedding_status`; before it
`embedding_status` was never re-armed, so no cycle existed. `reset-status:splade_status` came from
`4e9a17fa` (711). The unbounded loop itself predates both (516) — the latent structural defect that
converts one stuck document into a dead ingest pipeline.

The dense-score identity check flags **all ten** queries as systematically out of envelope —
per-pair deltas of **1.7e-2 to 6.8e-2** against a sandbox↔sandbox envelope of **1.8e-4**, roughly
200–400× larger.

**The leg attribution above stands. The causal conclusion first drawn from it does not — it was
written on 2026-07-31 and RETRACTED the same day.** The original wording read: *"the cause is the
embedding inference path differing between the dev stack and the Sandbox — same weights, different
execution,"* refuting the HNSW-tail-churn and FP16-vs-FP32 hypotheses. A stress-test pass
(tempdoc 801 §D10) recomputed the deltas from the raw captures and found **both halves of that
sentence unsupported**:

- **"Different numbers from the same weights" does not fit an execution-path cause.** Documented
  CPU-EP↔CUDA-EP divergence is ~1e-5–1e-4 — two to three orders too small. Decisively, **65 of 75
  shared (query, doc) pairs shift in the *same direction*** (mean +2.2e-2 in cosine terms, after
  converting out of Lucene's `1/(3−2·cos)` euclidean score, which makes the anomaly ~15% *larger*
  than the raw figure). Floating-point divergence — EP, TF32, precision, driver, kernel selection —
  is zero-mean and symmetric. A one-directional systematic shift is not a numerics signature.
- **"Same weights" was never established.** `EmbeddingFingerprint` hashes exactly one file, chosen
  by a `Files.isRegularFile` check that prefers the FP16 model whenever it exists on disk and
  **never asks which file the session actually loaded**. FP16-on-CUDA, FP32-on-CUDA (a documented
  fallback when FP16 session creation fails) and FP32-on-CPU are all indistinguishable under
  `f1d0f4ec…`. The sidecar JSONs that set truncation length, pooling and query/passage prefixes are
  not hashed at all, and this round logged all three as degraded/undeclared.

**Consequence: the earlier refutation of the FP16-vs-FP32 hypothesis is also withdrawn**, because
it rested entirely on this fingerprint. Finding 5 is therefore **NOT attributed**. The defensible
statement is narrower: *something structural differs between the two environments — most plausibly
truncation, prefixes or precision — and neither environment currently records enough to say which.*

What the round did establish, and which is worth keeping: the divergence is confined to the dense
leg, pooling and L2 normalisation happen in Java after the ONNX graph (identical bytecode both
sides, so excludable), and the ORT batch size is a fixed constant rather than VRAM-derived — which
eliminates the "big dev GPU vs paravirtualised GPU picks a different batch" hypothesis.

### B8.1 The convergence tempdoc went stale and the round did not notice for two hours

mechanical check and would have failed loudly at staging time.

### B8.2 `/start` does not name the three highest-signal staged documents

The staged `/start` skill's step 1 says to read `coverage-brief.md`, `validation-mode.md`,
`sandbox-environment.md`, and `staging-gaps.md`. It does **not** mention `charter.md`,

**Change:** `/start` step 1 must enumerate all staged authority files, or state "read every

### B8.3 `staging-gaps.md` reported "None" while a documented asset was missing

`staging-gaps.md` said "None — all documented assets staged." `tools/` contained only

### B8.4 Trace spans cannot attribute shape-routing findings

F6 is a shape/labelling defect on `POST /api/chat/dispatch`, whose behaviour is selected by
a `shapeId` **in the request body**. Trace spans record only `http.method`, `http.target`,
`http.status_code` and a few runtime attributes. The round could therefore prove *which
endpoint* was called but not *which shape was requested*, and had to stop at "not
determined in-sandbox."

**Change:** add `justsearch.chat.shapeId` as a span attribute on the dispatch handler. This
is a one-line instrumentation change that converts a whole class of finding from
"undetermined, needs source access" to "attributable from the round's own evidence."

### B8.5 The GUI harness has no absolute-coordinate click, and the folder picker needs one

`click.ps1` asserts foreground focus on the *JustSearch* window and fails closed when a
modal **native** dialog owns the foreground — which is exactly the state after clicking
"Add Folder." Adding a watched folder through the real UI is a required journey
(`sandbox-CLAUDE.md` phase 7) and is unreachable with the staged tools.

The round wrote an inline `SetCursorPos` + `mouse_event` P/Invoke helper. Two further
mechanics cost attempts: typing a path and pressing Enter **navigates into** the folder
rather than selecting it (a second action on "Select Folder" is required), and the picker's
`Folder:` field is pre-focused so the paste must not be preceded by a re-focus.

**Change:** add `click-abs.ps1` (or an `-Absolute` switch on `click.ps1`) to `gui/`, plus a
documented "add a watched folder through the native picker" recipe. Every fresh-install
round needs this.

### B8.6 Pixel coordinates drift when the composer grows — and this nearly produced a false finding

Pasting a query into the unified-chat composer expands the textarea and pushes the
escalation ladder **down**. A ladder coordinate captured before typing misses after typing.
The round's first Delegate click landed on nothing, the surface ran a plain search instead,
and the obvious reading was "the Delegate rung is a dead affordance" — a HIGH-severity
false finding.

What prevented it was `gui/README.md`'s own rule (*assert, don't guess, that a click
landed*) plus `GET /api/action-ledger` showing **no entry** for the click. This is the
single highest-value debugging affordance in the harness and it worked exactly as intended.

**Change:** add as gotcha #4 in `gui/README.md` — *select the rung/mode first on an empty
composer, then type*; and re-locate coordinates from a screenshot taken **after** any text
entry, never before.

### B8.7 Token cost: the round repeated the exact mistake `gui/README.md` warns about

`gui/README.md` records that "a whole round reading 74 full-resolution screenshots when
`crop.ps1` was staged the entire time was the dominant token cost of that round." Round 8
read roughly **70** full-resolution captures (1040×709 ≈ 1 k image-tokens each, plus four
1520×823 desktop shots at ≈ 1.7 k) — on the order of **70–80 k tokens** — while invoking
`crop.ps1` only about nine times. Crops cost 5–10× less (e.g. a 1500×72 status-bar strip
≈ 144 tokens). Perhaps 20–25 k tokens were avoidable: most re-checks needed one region
(a status bar, a progress line, a button label), not a whole surface.

There is also a **structural conflict** the README does not acknowledge: the mandatory
evidence review (`evidence-review.v1.json`) requires **opening every credit-eligible
screenshot at least once**, which pulls directly against the crop-first advice. In round 8
that meant 61 full-resolution reads were unavoidable *by policy*.

**Change:** add a downscale/thumbnail mode to `crop.ps1` (it currently only magnifies —
`-Scale` is `[int]` with minimum 1, so it cannot shrink). A `-Scale 0.5` or `-Thumb` mode
would let the review pass read many images cheaply and zoom only where a claim is in doubt,
resolving the conflict rather than trading one gate off against the other.

### B8.8 The install-state fingerprint fires on the round's own install

After the candidate is installed at step 1, every later `collect-evidence.ps1` run prints
"WARNING: JustSearch already appears to be installed on this system … known round defect."
Correct by construction, but it cannot distinguish *installed by this round, minutes ago*
from *pre-existing contamination*, so after step 1 it is pure noise that trains the reader
to skim a warning block that also contains the (important) elevation notice.

**Change:** have `collect-evidence.ps1` record an install marker on its first run and
downgrade the warning to an informational line on subsequent runs within the same round.

### B8.9 The non-elevated requirement cannot be satisfied by the round it is addressed to

`sandbox-CLAUDE.md` ("Run this round non-elevated") and `KICKOFF.md` rule 1 both address
the round, but Windows Sandbox's `WDAGUtilityAccount` **is** an administrator and the
session was already elevated before anything was installed. No in-sandbox action can
comply.

`collect-evidence.ps1` detects and reports this precisely and prescribes what to record —
that part works well. The instruction wording does not.

**Change:** address the requirement to the host launcher (which controls the posture), or
state plainly that it is unachievable under the current posture and that the round's only
duty is to record it. Consequence for round 8, recorded: UAC observation was **structurally
unobservable**, and any permission defect only a standard user would hit is masked
(`green-masked-destructive`).

### F7 root cause (host-side, 2026-08-01; claims re-verified at source by the orchestrator)

**PR #350 (`6a6e4835`, tempdoc 617) flipped the packaged shell's Head launch from
`-Djustsearch.prod=false` to `-Djustsearch.prod=true` (`lib.rs:746`; v0.1.0 shipped `false` at
its line 677, with a "TODO: re-enable for production release" comment). That switch is correct
in intent — v0.1.0's whole loopback API was UNAUTHENTICATED (rounds 8/9 logs confirm
`prodMode=false, tokenGenerated=false`) — but it armed a filter the shipped frontend could
never satisfy: the shell-v0 Lit rewrite NEVER adopted `api/http.request()`'s token attachment.**

- The token chain is intact through four hops — Head mints per-boot token
  (`HeadlessApp.java:363-364`), publishes via runtime manifest (`RuntimeManifestPublisher`),
  shell watches the manifest and exposes a `session_token` Tauri command (`lib.rs:920-958`,
  `:1071-1086`), and `api/http.ts:189-215` + `streams.ts` attach `X-JustSearch-Session`
  (`LocalApiServer.java:68`). **The chain dies at the last hop**: shell-v0 has ~50 non-GET call
  sites across 18 files, all bare `fetch` — `searchState.ts:564` (whose `HTTP ${res.status}`
  error render IS the round's red box), `plugin-api/capabilities/data.ts:35-48` (`performFetch`,
  the `host.data.fetch` seam behind every surface's `doFetch`), `OperationClient.ts:194`, etc.
  `SecuritySurface.ts:279-280`'s comment claims "doFetch injects the token" — the injection
  does not exist. Only chat/agent streaming (`consumeShapeStream`) attaches it.
- `ApiSecurityFilters` itself is byte-identical to v0.1.0 (#350 added only the upgrade-lease
  admission); `http.ts` untouched since v0.1.0. No header rename (the round's
  `X-Justsearch-Session` worked via case-insensitive header lookup).
- **Why nothing caught it:** the enforcing side and the attaching side were never run
  together — dev/vite, ui-shot, and RAIL all run backends without `-Djustsearch.prod`, so any
  dev-mode step passes vacuously (`green-masked-destructive`). The eslint rule that names this
  exact hazard (`no-restricted-globals: fetch`, eslint.config.js:172) has been at `'warn'`.
- **Fix direction (do NOT revert `prod=true`):** attach the token at the two covering seams —
  `performFetch` in `data.ts` and `searchState.ts` — then sweep the remaining bare-fetch sites
  onto the same helper and flip the eslint rule to `'error'`. Regression homes: (static) the
  eslint error + a ui-web unit test that a non-GET through `host.data.fetch` carries the
  header; (live) extend `verify-installer-nsis-win.ps1` (already boots the payload with
  `prod=true`, stops at readiness) to assert headerless POST → 401 and headered POST → 200;
  the full webview half stays with the sandbox round / future tauri-driver work.
- **Security note for the threat model:** `GET /api/mcp/token` returns the live token
  unauthenticated by design (`LocalApiServer.java:600,680-682` — how the MCPB bridge
  authenticates). The enforcement is therefore browser-threat defense-in-depth (a cross-origin
  page cannot read the GET response, so its POSTs stay rejected), NOT a local-process
  authorization boundary; `ApiSecurityFilters.java:189-190`'s "only the legitimate desktop UI"
  claim overstates it and should be corrected when the 617 threat-model section lands.

### F3/F2/F4 root cause (host-side, 2026-08-01; claims re-verified at source by the orchestrator)

**Same commit, same flag as F7 — and the round's packs-registry hypothesis is REFUTED.** There
is no packs registry in the chat-model resolution chain at all; the chain is one link long:
`RuntimeActivationService.runActivate` reads `settingsStore.load().getLlmModelPath()` and fails
`MODEL_PATH_REQUIRED` when blank (`RuntimeActivationService.java:537-542`). `installed-packs.v1.json`
is written only by offline `.justpack` import (`PackInstallOps.upsertPack`) — empty is the
NORMAL state for every Install-AI user, including round 8's working fresh install. The error
text "Import a models pack first" is misleading copy, not a description of the dependency.

- **The real mechanism:** `UiSettingsStore.resolveMode()` makes `justsearch.prod=true` imply
  `IN_MEMORY` settings (`UiSettingsStore.java:168-172` — "prevent settings contamination during
  verification"): `load()` returns fresh defaults, `save()` is a silent no-op. PR #350's
  `prod=true` flip therefore turned the shipped app's settings store into a black hole:
  `llmModelPath` is always blank at activation; re-running Install AI writes the contract file
  (plain file IO, works) but `applySettings`' `settingsStore.save()` is discarded — exactly the
  round's "ledger repaired, activation still dead" observation; `POST /api/settings/v2` returns
  409 `SETTINGS_READ_ONLY`, so the manual workaround is structurally impossible; and
  `RuntimeSpecStore` writes through the same store, so `core.set-chat-enabled` can never
  persist — **that is F4's failing operation**. Theme/density/excludePatterns are equally dead.
- **Not upgrade-specific:** a fresh install of this candidate is equally dead. v0.1.0 worked
  solely because it shipped `prod=false` (settings READ_WRITE); its resolver/applySettings code
  is byte-identical to main. Proof from the round's own logs: zero config keys resolved with
  source `ui_settings` across all three backend logs; `gpu.layers=99` came from VRAM
  auto-populate, not settings.
- **F2 explained separately:** install status is never rehydrated from the contract;
  `maybeRecomputeInstalledFromDisk()` re-plans and flips `installedFully` only when zero
  downloads remain. 0.2.0's registry added `ort-native-cuda12-v1.24.3.zip` (167,772,095 bytes =
  the round's "160 MB"), so the upgraded machine had exactly one pending download →
  `installedFully:false, packages:[]`. Generalization worth its own fix decision: **any
  registry addition in a new version makes a fully-installed prior install read "Not
  Installed" until a re-run.**
- **`chunkEmbeddingReady` true→false is a truth-telling change, not state loss:** v0.1.0
  computed it from status-field counts; HEAD computes it from actual `chunk_vector` artifact
  presence (tempdoc 717 "status lies", `IndexStatusOps.java:636`). The new probe is honest
  about an index whose chunk vectors were always incomplete.
- **Fix direction:** (1) delete the implicit prodMode→IN_MEMORY rule — both prod-mode
  harnesses (`build.gradle.kts:1765`, `verify-installer-nsis-win.ps1:450`) already pass the
  explicit `-Djustsearch.ui.settings.mode=IN_MEMORY` themselves, so nothing changes for them;
  update `UiSettingsStorePersistenceModeTest` deliberately as the contract change; belt-and-
  braces `-Djustsearch.ui.settings.mode=rw` in `lib.rs`. (2) Defense-in-depth: contract-derived
  fallback in `runActivate` when `llmModelPath` is blank (the Worker already does exactly this,
  `KnowledgeServer.java:926` — why ONNX survived the upgrade while chat died), plus honest
  message text. A packs-registry migration is NOT needed and would be wrong — nothing reads it.
- **Regression homes:** live-stack integration test booting `prod=true` with NO settings-mode
  override on a seeded v0.1.0-shaped data dir, asserting activate ≠ MODEL_PATH_REQUIRED and
  settings ≠ 409; unit guard on `resolveMode()` (prod=true + no override → READ_WRITE); and a
  packaging-tier assert that a booted installed payload resolves ≥1 `ui_settings`-sourced
  config key — the round log's zero-count is the single most diagnostic, machine-checkable
  signal of this whole class.

### R11-F2 [BLOCKER, build-level] After a backend restart the shell keeps a dead session token, and every UI mutating call 401s forever

**The round reported this as "two endpoints (unlock/lock) don't attach the token". The trace file
it collected shows something much larger, and I could root-cause it from source.**

Head restarted at 05:04:45 local and published its new manifest at 05:04:46.697
(`logs/headless-backend.log:1,175`). From **05:04:46.89 onward every single webview-originated
POST 401s** — `/api/chat/agent/virtual-operations`, `/api/action-ledger/events` (dozens),
`/api/operations/core.resolve-path-hash/invoke`, and later `/api/conversations/encryption/unlock`
and `/lock` — all with sub-millisecond durations, the fingerprint of rejection at
`ApiSecurityFilters` before any work. The only 200s after that moment are the round's own
PowerShell calls carrying a freshly fetched token. Encryption unlock is not a special case; it is
simply the first 401 a human could *see*, because the background posts fail silently.

Mechanism, established at source:

- `set_session_token` (`modules/shell/src-tauri/src/lib.rs:135-147`) is **first-write-wins** and
  has no restart override.
- `note_instance_and_detect_restart` (`:113`) detects a new Head incarnation and calls
  `force_set_port` (`:130`) — **port only**. Tempdoc 637 #1 fixed the port on restart, added
  `test_force_set_port_overrides_first_write_wins` (`:1660`), and left the token behind. The
  asymmetry is explicit in the code and in its own tests.
- `reset_for_restart` (`:80-93`) *does* clear the token — but it is the **updater** path only;
  a crash or a kill-restart never calls it.
- `read_manifest_if_present` (`:1026`) does no pid/instance validation, and the previous Head log
  ends abruptly with **zero shutdown markers** — force-killed, so
  `RuntimeManifestPublisher.close()` never removed the stale manifest. A shell starting while
  that file is on disk latches the **previous boot's** token on its first 100 ms tick and can
  never replace it.
- The frontend cannot recover either: `api/http.ts:199-237` caches the token permanently once
  obtained (correctly, for its own problem), the one subscriber to the
  `justsearch://backend-restart` event (`main.jsx:151`, tempdoc 637 — a full-page reload;
  an earlier grep missed it by filtering to `*.ts`) cannot help, because the reload re-resolves
  from the same latched Rust state; and no 401 path invalidates the cache.
  CORRECTION 2026-08-04: this bullet originally claimed no subscriber exists — wrong file-type
  filter; immaterial to the root cause (the Rust latch), but recorded for accuracy.

Both entry routes — shell survives a Head restart, or shell restarts onto a stale manifest — end
in the same latched-dead-token state, and both are defects in the same function. Which one this
round hit is not established and does not change the fix.

**Fix shape (design owed):** token adoption must follow the same instance-change rule the port
already follows (a `force_set_session_token` on detected restart), the manifest reader must
refuse a manifest whose `instanceId` does not belong to the current run (or whose pid is dead),
and the frontend needs one-shot token re-resolution on a `UI_TOKEN_REQUIRED` 401 so a latch can
never be permanent. **Regression homes:** a Rust unit test mirroring
`test_force_set_port_overrides_first_write_wins` for the token; a ui-web test asserting a
`UI_TOKEN_REQUIRED` 401 triggers exactly one re-resolve-and-retry; and — the tier that would
actually have caught this — a restart leg in the packaged verify lane
(`scripts/ci/verify-installer-nsis-win.ps1` already asserts token enforcement; it does not restart
Head and re-assert).
